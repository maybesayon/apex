# Deploying APEX

Getting a link you can send to testers. Everything here is free.

| Piece | Service | Why |
|---|---|---|
| Frontend | **Vercel** | Built for Next.js; deploys on git push |
| API | **Render** | Free web service, 750 hrs/month |
| Database | **Neon** | 0.5 GB Postgres, **no expiry** |

> **Do not use Render's free Postgres.** It is deleted 30 days after
> creation, with a 14-day grace period. Free compute from Render, free
> database from Neon.

---

## 1. Database (Neon)

1. Sign up at [neon.com](https://neon.com) — no card required.
2. Create a project — region **AWS US East 1 (N. Virginia)**, to match
   the API region in `render.yaml`. Copy the connection string.
3. Rewrite the scheme for SQLAlchemy:

   ```
   postgresql://user:pass@host/db          ← what Neon gives you
   postgresql+psycopg://user:pass@host/db  ← what to paste into Render
   ```

   `db.py` normalises both `postgres://` and `postgresql://` onto the
   psycopg driver automatically, so pasting Neon's string verbatim works.

**Verified against a real Neon database:** all 206 tests pass on
PostgreSQL 18.6, including through Neon's connection pooler.

Neon suspends compute after 5 minutes idle, so the 100 monthly
compute-hours only burn while someone is actually using the app.

---

## 2. API (Render)

1. New → **Blueprint**, point it at this repository. Render reads
   [`render.yaml`](render.yaml).
2. Set the variables marked `sync: false` in the dashboard:

   | Variable | Value |
   |---|---|
   | `DATABASE_URL` | the Neon string from step 1 |
   | `APEX_CORS_ORIGINS` | your Vercel URL (fill in after step 3) |
   | `FINNHUB_API_KEY` | optional |
   | `ANTHROPIC_API_KEY` | optional |

   `APEX_SECRET_KEY` is generated by Render and persists across deploys.
   **Changing it signs every user out.**

3. Deploy. Check `https://<your-api>.onrender.com/health`:

   ```json
   { "status": "ok", "auth": { "env": "production", "cookie_secure": true },
     "warnings": [] }
   ```

   A non-empty `warnings` array means something is misconfigured — it
   flags insecure cookies and a missing secret key explicitly.

Migrations run on every boot (`alembic upgrade head`), so a deploy can
never serve a schema it has not migrated to.

## 3. Frontend (Vercel)

1. Import the repository at [vercel.com](https://vercel.com).
2. **Root Directory: `frontend`** — this is the one setting people miss.
   Everything else is detected.
3. Add one environment variable, for **all** environments:

   | Variable | Value |
   |---|---|
   | `APEX_API_ORIGIN` | `https://<your-api>.onrender.com` |

   > This is read by `next.config.ts` **at build time**, so changing it
   > later requires a redeploy, not just a restart.

4. Deploy, then go back to Render and set `APEX_CORS_ORIGINS` to the
   Vercel URL.

### Why the proxy matters

`next.config.ts` rewrites `/api/*` to the Render service. The browser only
ever sees the Vercel origin, so the session cookies stay `SameSite=Lax`
rather than being weakened to `SameSite=None`. Without this, cookie auth
across two origins needs `Secure` plus `SameSite=None`, which is strictly
worse. Do not replace the proxy with a direct `NEXT_PUBLIC_API_URL`.

---

## 4. Keep it awake

Render free services sleep after **15 minutes** idle and take about
**50 seconds** to wake. A tester clicking your link into a minute of blank
screen will assume it is broken.

Point a free uptime monitor ([cron-job.org](https://cron-job.org),
UptimeRobot) at `https://<your-api>.onrender.com/health` every 10 minutes.
Staying awake all month costs ~744 of the 750 free hours, so this uses the
allowance on one service — which is the right place for it.

## Known limits for a beta

Be honest with testers about these.

**Authentication is private-beta grade.** No email verification, no
password reset, no rate limiting or lockout on login. Fine for a small,
closed group of people you know. Not fine for a public link.

**Alert history is not durable.** `tv_alerts.json` is written to the
container's disk, which Render wipes on restart. Accounts, positions,
watchlists and journals are all in Postgres and safe; only TradingView
webhook history is lost.

**The S&P constituent cache rebuilds after each restart.** The first broad
scan after a cold start is slower while it re-scrapes. Harmless.

**A running scan does not survive a restart.** Jobs run in the API process,
so a deploy kills an in-flight scan. Stale jobs are marked failed rather
than spinning forever. See §2.1 of [`MIGRATION_PLAN.md`](MIGRATION_PLAN.md).

**Market data comes from unofficial sources.** `yfinance` and
`tradingview-ta` are scrapers. Fine for personal and test use; a real ToS
question before anything commercial.

## Local development

```bash
# API
uvicorn api.main:app --reload --port 8000

# Frontend
cd frontend && npm run dev
```

Defaults to SQLite at `./apex.db` and generates a development signing key
in `.apex_dev_secret` (gitignored), so local sessions survive a restart
with no configuration.
